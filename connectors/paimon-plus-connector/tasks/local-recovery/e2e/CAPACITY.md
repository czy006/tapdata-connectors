# 固定桶全量提交、CDC 与静默恢复的容量样本

2026-11-19 在 macOS arm64、JDK 17.0.20、Paimon 1.3.2 和本机文件系统上实测。同一工作树构建分别关闭和启用 `localRecoveryDir`。每次用新 JVM 和新 warehouse；三轮中交替先跑哪种模式。测试使用 `PaimonService` 的真实建表、写入、全量结束、后台 CDC 提交和启动恢复入口。仅 TapData 上下文、节点 KV 及日志由夹具提供。

固定两桶，单表以整数 id 为主键，16 批 × 512 行，合计 8,192 行。值由 id 加固定字符串构成，容易压缩。`writeBufferSize=8` MiB，`enableAutoCompaction=false`，`commitIntervalMs=500`，`batchAccumulationSize=640`，`enableAsyncCommit=true`。每个 JVM 使用 `-Xms256m -Xmx512m`。全量结束后，一次写入前 64 个已有键的新值，不再投递数据或心跳，轮询第二个 snapshot。每轮在两个 snapshot 上都用 Paimon 普通读取逐键检验值、缺失键、多余键及重复键。

| --- | ---: | ---: |
| 全量末尾前可见 snapshot 数 | 0 | 0 |
| 全量末尾后可见 snapshot 数 | 1 | 1 |
| 桶 0 / 桶 1 的数据文件数 | 1 / 1 | 16 / 16 |
| 桶 0 / 桶 1 的数据字节 | 35,111 / 35,034 | 52,555 / 52,169 |
| 数据文件总字节 | 70,145 | 104,724 |
| 单文件最小 / 下中位 / 最大字节 | 35,034 / 35,034 / 35,111 | 3,039 / 3,268 / 3,483 |
| 全量最后一批 ACK 后的 prepare 文件数及总字节 | 0 / 0 | 16 / 22,128 |
| 同一时刻恢复目录中全部常规文件字节 | 0 | 23,011 |

本次两种模式全量都只发布一个 snapshot。启用恢复后，每次 ACK 前 prepare 都产生原生数据文件，两个桶合计由 2 个增至 32 个。全量时间中位数从 1,108 ms 增至 1,576 ms，仓库数据文件总字节增至 1.49 倍。恢复目录采样点是最后一次全量 ACK 后，所有批次都仍待发布；统计逻辑文件大小，瞬时临时文件、文件系统块分配和 Paimon 仓库不计入这 23,011 B。

| 进程中止后无新输入的 `startLocalRecovery`，ms | 未测 | 915 / 983 / 962 |

全量时延取两段计时之和，覆盖全部 `writeRecords` 调用及 `afterInitialSync`，不含事件构造、文件计数和结果读取。堆来自每 2 ms 采样的整个 JVM 的 `MemoryMXBean`，受 GC 时机影响；CDC 可见时间的快照轮询间隔为 5 ms。静默恢复每轮另起两个进程，第一个在 16 批 ACK 后、省略末尾提交、调用 `Runtime.halt(42)`，第二个启动后直接恢复。恢复时延只计 `startLocalRecovery`，恢复完成后读回全部 8,192 个键值。各阶段定时使用单调时钟。

该样本用于估算小批次带来的文件放大。关闭模式来自同一构建的旧逻辑分支。更大行宽、真实源批次、自动 compaction、长时间 spill、多表和远端 warehouse 的资源曲线，以及真实 Mongo 位点和线上规模的 SLA 仍需单独验收。测试运行时主机还承担其他构建工作。

## 复现

在同一工作树完成模块的 `PaimonStartupRecoveryIntegrationTest` 后，在本目录执行：

```sh
JAVA_HOME=/path/to/jdk17 RUNS=3 BATCHES=16 BATCH_SIZE=512 bash run-service-benchmark.sh
```

脚本复用该测试的依赖和持久化 KV 夹具，在临时目录编译、生成数据、核验每轮退出码并输出 `SAMPLE` 记录。每种模式使用相同数据；可调整三个环境变量检查不同样本。
